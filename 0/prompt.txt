### P3 Findings (substantive observations):

**P3 | correctness | `scripts/experiments/token_savings.py`:248 | `--summary` always prints JSON before the human-readable summary; `--json` flag only suppresses the human part**

When `--summary` is used *without* `--json`, the output is JSON blob followed by `--- Summary ---`. When `--summary --json` is used, only the JSON blob prints. This is intentional per the code, but the CLI UX is slightly odd: `--json` doesn't switch output format, it removes the non-JSON suffix from an already-JSON output. No data corruption, just a minor ergonomic surprise. Same pattern on lines 259-270 for the non-summary path.

Failure scenario: A user piping `--summary` output to `jq` without `--json` gets a parse error from the trailing human-readable lines.

**P3 | security | `src/entirecontext/core/decision_verify.py`:53-54 | Absolute path check does not catch relative traversal (`../../etc/passwd`)**

`Path(d).is_absolute()` rejects `/etc/passwd` but not `../../etc/passwd`. However, the API surface is the local CLI (`ec decision verify-docs --dir`) invoked by the repo owner — this is a same-privilege-level operation where the user already has filesystem access. The `root / d` join resolves within the filesystem namespace the user controls. No privilege escalation. The absolute check is a reasonable guardrail against accidental misuse (e.g., pasting a full path when a relative one was intended), not a security boundary. Not a real vulnerability, just noting the scope of the defense.

**P3 | correctness | `src/entirecontext/core/decision_verify.py`:119 | Broadened `sqlite3.Error` catch masks more failure modes, but acceptably**

`_get_source_schema_version` now catches `sqlite3.Error` (base class) instead of `sqlite3.OperationalError`. This means `sqlite3.DatabaseError` (corrupt file), `sqlite3.InterfaceError`, `sqlite3.ProgrammingError` all return `0` instead of propagating. Given the function's purpose (graceful degradation when schema_version table is absent or unreadable), returning `0` for all these cases is reasonable — the caller (`promote_decisions`) then fails on the schema version mismatch check, producing a clear error. The broader catch aligns with the new `test_corrupt_file` test case.

### Verified clean:
