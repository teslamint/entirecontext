**VERDICT: REVISE**

**Overall Assessment**: The design direction is correct — the migration is straightforward and the core decision (2.x only, new ADR, separate branch) is sound. However, the design has three gaps that would cause rework if an executor followed it as-is: an incomplete file scope, unassessed dependency landscape changes, and ambiguous change descriptions for `server.py` internals.

**Pre-commitment Predictions vs Actual**:
1. "Import path changes may be incomplete beyond server.py" → CONFIRMED: `docs/spec.md:40` missed
2. "Decorator API compatibility is the riskiest assumption" → VERIFIED SAFE: `.tool()` and `.run()` carry over unchanged
3. "Test mocks may reference old class names" → CONFIRMED: `tests/test_mcp_cmds.py:43,52` patches `_FASTMCP_IMPORT_ERROR`
4. "Transitive dependency changes" → CONFIRMED: `httpx` → `httpx2`, new `opentelemetry-api`, new `mcp-types` package
5. "Error variable naming stale" → CONFIRMED: `_FASTMCP_IMPORT_ERROR` and `FastMCP: Any` annotation remain

---

**Major Findings** (causes significant rework):

1. **Dependency landscape not assessed — new transitive deps in MCP 2.0**
   - Confidence: HIGH
   - Evidence: `pip install --dry-run 'mcp>=2.0.0,<3'` reveals MCP 2.0 depends on `httpx2` (replacing `httpx`), adds `opentelemetry-api>=1.28.0` (entirely new), and adds `mcp-types==2.0.0` (extracted types package). Also drops `httpx-sse` and `pydantic-settings`.
   - Why this matters: While the MCP extra is isolated (installed via `uv tool install`), these changes alter the dependency tree significantly. The `httpx` → `httpx2` transition is a Python ecosystem-wide shift that could cause conflicts if users have other packages in the same venv expecting `httpx`. The `opentelemetry-api` adds weight. These should be acknowledged in the ADR so future maintainers understand the dependency footprint change.
   - Fix: Add a "Dependency Changes" section to the new ADR documenting: `httpx` → `httpx2`, new `opentelemetry-api`, new `mcp-types`, dropped `httpx-sse` and `pydantic-settings`. Note that isolation via `uv tool install` mitigates conflict risk.

2. **No explicit verification step in the plan**
   - Confidence: HIGH
   - Evidence: The design asks `"Should we verify that MCPServer.tool() decorator works identically to FastMCP.tool()?"` — acknowledging uncertainty — but doesn't include a verification protocol as a plan step.
   - Why this matters: The migration guide confirms API compatibility, but the project has 119+ MCP tool tests that serve as the ground truth. Without an explicit "install mcp 2.0 in test env, run full test suite" step, the executor may skip empirical verification.
   - Fix: Add a verification step: (a) create a temporary venv or branch with `mcp>=2.0.0,<3`, (b) run `pytest tests/test_mcp.py tests/test_mcp_cmds.py tests/test_contract_sync.py -v`, (c) confirm all pass. This step should come AFTER the code changes and BEFORE the ADR/docs updates.

3. **Incomplete enumeration of `server.py` changes**
   - Confidence: HIGH
   - Evidence: The design says `"Change import, update class name, update error message"` for server.py. But `server.py` contains FIVE distinct references that need updating:
     - Line 10: `FastMCP: Any` type annotation → `MCPServer: Any`
     - Line 11: `_FASTMCP_IMPORT_ERROR` variable name → should rename (e.g., `_MCP_IMPORT_ERROR`)
     - Lines 13-15: import path (covered by design)
     - Line 17-18: `FastMCP = None` / `_FASTMCP_IMPORT_ERROR = exc` → update names
     - Line 20: `FastMCP("entirecontext")` → `MCPServer("entirecontext")` (covered by design)
     - Line 141: error message string referencing `'from mcp.server.fastmcp import FastMCP'` (covered by design)
     - Line 143: `from _FASTMCP_IMPORT_ERROR` → update if variable renamed
   - Why this matters: An executor reading "update class name" might change only line 20 and miss lines 10, 11, 17-18. The variable `_FASTMCP_IMPORT_ERROR` is referenced by tests (`test_mcp_cmds.py:43,52`), so renaming it requires coordinated test updates.
   - Fix: Enumerate all five change sites explicitly. If `_FASTMCP_IMPORT_ERROR` is renamed, list `tests/test_mcp_cmds.py:43,52` as a coordinated change.

---

**Minor Findings** (suboptimal but functional):

1. `docs/spec.md:40` — architecture diagram says `MCP Server (stdio, FastMCP)`, needs updating to `MCPServer`. Not listed in the design's file scope.
2. `tests/test_contract_sync.py:40-44` — `_FakeMCP` class name and docstrings reference `FastMCP.tool()`. Functionally correct (the fake captures `.tool()()` calls identically), but cosmetically stale.
3. `uv.lock` — committed lock file will need regeneration via `uv lock` after the `pyproject.toml` pin change. Standard practice but worth calling out for the executor.
4. Historical documents (`docs/retros/2026-08-19-mcp-serve-silent-failure-retro.md`, `docs/plans/2026-08-19-001-fix-mcp-serve-silent-failure-plan.md`) reference `FastMCP`. These are point-in-time records and should NOT be updated — the design should explicitly scope them out to prevent an overzealous executor from touching them.

---

**What's Missing** (gaps, unhandled edge cases, unstated assumptions):

- **Rollback plan**: If MCP 2.0 has a bug that breaks stdio transport, reverting is just a pin change + import revert, but this should be stated explicitly in the ADR's Consequences section.
- **MCP 2.0 maturity risk**: `mcp==2.0.0` is the ONLY 2.x release (verified via `pip index versions mcp`). The design should acknowledge this is a .0 release and note whether the project's CI would catch regressions from future 2.x point releases.
- **`mcp.run()` transport parameter migration**: MCP 2.0 moved transport-specific parameters from the constructor to `run()`. The current code calls `mcp.run()` with no arguments (stdio is default), so this is safe — but the design should explicitly confirm this assumption so the executor doesn't wonder.

---

**Ambiguity Risks**:

- `"update class name"` → Interpretation A: change only line 20 (`FastMCP("entirecontext")` → `MCPServer("entirecontext")`). Interpretation B: change all `FastMCP` references including the type annotation at line 10 and the variable at line 11.
  - Risk if Interpretation A chosen: stale variable names, confusing code. Tests at `test_mcp_cmds.py:43,52` still work but reference a misleadingly named variable.

- `"Update any mock patterns if needed"` → Interpretation A: check test_mcp.py mocks (no changes needed). Interpretation B: also check test_mcp_cmds.py patches of `_FASTMCP_IMPORT_ERROR` and test_contract_sync.py's `_FakeMCP`.
  - Risk if only Interpretation A checked: `_FASTMCP_IMPORT_ERROR` patches in test_mcp_cmds.py silently pass because the variable was NOT renamed (a consistency miss, not a test failure).

- The `httpx` → `httpx2` transition: is the project's CI environment clean enough that this won't conflict? Since CI presumably installs the `[mcp]` extra in isolation, this should be fine, but worth a quick check.
